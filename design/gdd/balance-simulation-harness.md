# Balance Simulation Harness

> **Status**: Designed (CD-GDD-ALIGN CONCERNS applied 2026-11-14; independent `/design-review` not yet run)
> **Author**: user + Claude design session, with specialist consultation
> **Last Updated**: 2026-11-14
> **Last Verified**: 2026-11-14
> **Implements Pillar**: Earned Rarity (measures the 1-in-20 target); supports every pillar by turning a design claim into a measurement with its uncertainty shown

## Summary

The Balance Simulation Harness is a headless tool, not a game system: it plays thousands of seeded runs through System 5's own command interface with a **player policy** (automatic arrangement, door and reward choices), and reports what the design claims, with confidence intervals. The thin MVP form answers the questions the other GDDs deferred to it: how often a competent, committed player wins the boss and reaches a run-defining Detonation (the 1-in-20 target), whether the Purple door's price is real, whether the certain buff earns its place, and how the commitment lean, the pool and the fight lengths behave. Its core is engine-free and shared with the game, hosted as a standalone .NET console for bulk sweeps and checked against Unity by a small set of parity fixtures; every report is canonical text with a checksum, stamped with every version, and byte-identical for the same inputs at any thread count. In the MVP only the harness's own correctness is a blocking gate; the balance results are advisory evidence read through a pass, fail or inconclusive rule on the interval, never on a point estimate.

## Overview

Almost every system GDD defers a number to "System 35 measures it": the key-item share and the lean cap (System 18), the Purple door's price against its reward and the buff's worth (System 17), the burst bound and the template floors (System 16), the Gold curse as a bet (System 19, Vertical Slice), the distribution of chain sizes and actions per fight that System 29's ladder thresholds need, the stacking cap (System 10). The prototype could not answer any of these, and a solo developer cannot tune them by hand-playing: the 1-in-20 target is a probability of about 0.05 and needs thousands of runs to see. The harness exists to make those answers cheap and trustworthy. It drives the same run machine as the UI through the same command interface (System 5 line 190: "the command interface is the harness's interface"), so it measures the real rules, not a model of them. A policy plays the part of the player; a driver loops until the run ends; accumulators count; a canonical report states the results with their intervals and the exact versions that produced them. It is built from the engine-free core and pulls in no engine, so it can run thousands of runs per second per core and give the same bytes every time. The harness is a developer tool: it has no screen, no player-facing text and no effect on the shipped game.

> *Specialists consulted for this section: systems-designer, economy-designer, tools-programmer, game-designer, gameplay-programmer, qa-lead, technical-director (2026-11-14). Their findings are applied below; where they disagreed the user decided (Core Rules 2, 6, 7, 17).*

## Player Fantasy

The "player" here is the designer. They ask a question of the design, such as whether the Purple door is worth its danger, and they get an answer they can stake a decision on: the same answer every time, with its uncertainty printed next to it, and with a clear "I could not tell" when the data is not enough. **The harness never flatters the design: it says what it measured, how sure it is, and what it could not assess.**

*Pillar anchors.* Pillar 3, Earned Rarity: the perfect run is rare by default and reachable through skill, which is a claim about a probability; only a simulation with a skill axis can check it. Pillars 1, 2, 4 and 5 each carry a number (the lean, the payoff size, the visible bet, the price) that this system tests. *Guardrails:* a result without its sample size and interval is not a result; a metric with no policy or too few runs reads NOT ASSESSED, never zero or pass; a policy sees only what a player sees; the same inputs always give the same bytes; a balance verdict never rests on a bot's strength alone; the harness informs and the playtests decide, so no go/no-go criterion is met by simulation.

*Risks the design guards against:* a weak or lucky bot that makes every number meaningless; tuning that overfits one policy or one seed set; a gate that passes on a point estimate; a harness that measures a runtime that is not the shipped one; results that cannot be reproduced.

## Detailed Design

### Core Rules

1. **A tool that reads the real game.** The harness is not a model of the rules. It builds the same `RunSession` the game builds (System 5 Rule 2, no statics), supplies the seed through the seed port (System 5 Rule 13; zero is a valid seed), and sends commands through the same facade (`Execute(cmd)` returning Accepted, NoEffect, Rejected or TechnicalStop). It has no privileged path: a command the UI could not send is not sent. The harness is single-purpose and ships nothing to players.
2. **Hosting: one source, two compilers, parity fixtures (user decision).** The engine-free core sources live once under `Assets/_Project/Scripts/Core/` in an assembly with `noEngineReferences`; Unity compiles them as usual. The harness logic (policies, driver, accumulators, statistics, report writer) lives in a second `noEngineReferences` assembly, `Project05.Harness` (the assembly name is NOT SOURCEABLE until the architecture ADR). The harness assembly is excluded from player builds (an Editor-only platform or a define constraint), a criterion checks that a player build contains no harness types, and only the core ships. A standalone **.NET class library** under `tools/sim/` includes the same `.cs` files by glob (`netstandard2.1`, `LangVersion` pinned to the level Unity compiles, an explicit setting because .NET 10 defaults to a newer level), and a **`net10.0` console** hosts the bulk sweeps. `.NET` projects never sit inside `Assets/` (Unity would import `bin/` and `obj/`), the solution is not named like Unity's generated one, and no root `Directory.Build.props` is added (it would leak into the IDE builds of the Unity projects). The sweeps need no Unity licence and run while the Editor is open (the Editor is never killed; batchmode on the open project is not used). A small set of **parity fixtures** (Rule 18) runs as Unity EditMode tests and in the console from the same files; equal results are the proof that the .NET build measures the shipped logic. An ADR records the .NET profile, `LangVersion`, API compatibility level, the scripting backends in scope, the banned-API list, the checked-arithmetic policy, the canonical text encoding, the parity definition and which runtime is authoritative when they disagree (Unity).
3. **The driver.** `RunDriver.Play(seed, policy, config) -> RunResult` builds a fresh session and loops: read the `RunView`, call `policy.Decide`, send the command through the facade with the current serial (the harness wraps the serial so a policy never sees it), until the run is Ended, Stopped or Abandoned, or a step cap of 2,000 commands is reached (`DriverStall`, never silent). A `Rejected` command is retried at most 3 times with the policy's next choice and then counts as `DriverStall`. A `TechnicalStop` is counted, its first diagnostic kept, and the run reported in the denominators (it is never silently dropped). A Draw counts as a loss. The harness supplies its own `runId` counter (the live game holds it in the Unity layer). Sessions are created fresh per run in the MVP; a `Reset(seed)` reuse path is **[VS]** and needs a reset-equals-fresh test.
4. **The policy interface.** `Policy.Decide(in RunView, PolicyContext) -> Command` is a pure function that returns exactly one legal command. `RunView` is a read-only, by-value projection built by one adapter: the phase, the room, the legal-command list taken from the run machine's own legality query (never recomputed by the policy), the player-visible fields (the three door cards with tier, certain buff, danger, class counts and suggested hero; the shelf cards; the tray; each hero's grid; the commitment reading) and read-only query handles `Preview` and `Forecast`. Each policy declares the views it needs (`requiredViews`) and cannot receive more. `PolicyContext` holds a dedicated policy random stream (derived from the run seed by a distinct label and used only by policy code), the skill parameter `s` and the move budget (a count). It holds no clock. **A `RunView` and a typed, immutable `RunConfig` do not exist yet in any GDD**: this GDD requires System 5 to define both (Open Questions); the harness cannot start without them.
5. **What a policy must never see or do.** No RNG state, stream, clone or preview of an unrevealed draw; not the seed; not the stored row or offer before the player would see them; not the bound intents beyond what the UI shows; no catalog internals beyond player-visible information; no run counters or metrics (System 5 Rule 16: never read by gameplay); no `Restore` (only the harness may use it for what-if experiments); no mutable references; no wall clock or environment reads. It is proven in three layers: **structural** (the policy assembly references only the view types, checked by an assembly-reference test); **perturbation** (two views that differ only in hidden state give bit-identical commands); **stream audit** (the gameplay streams' draw counts are identical with and without the policy's queries, so `Preview` and `Forecast` consume nothing).
6. **The policy ladder (user decision: MVP is tiers 0 to 2).** Each policy is a record of per-decision strategies (door, shelf, claim, arrange, start), so a degenerate policy is a one-field override of Competent. A **modifier** such as `CellBudget(c)` (non-innate items may occupy at most `c` cells in total; the arrangement search and `AutoPlace` refuse a placement beyond it) applies to any policy, so two policies can be compared at an equal budget (question 14). **Tier 0:** `RandomLegal` (uniform over the legal list; the floor and a soak test). **Tier 1, the degenerate set:** `AlwaysSafestDoor`, `AlwaysPurple`, `NeverSkip` (and `AlwaysSkip`), `NeverRearrange` (automatic placement only, no rotation), `OneHeroStack` (every item on one hero), `IgnoreCommitment`, and the pair used by question 2: `IgnoreRoster` (Competent with the roster-fit term of the door score set to zero) and `AnswerRoster` (Competent with that weight doubled and the arrangement search scored against the chosen door's roster). **Tier 2:** `Competent`. **[VS]:** `Strong` (a larger budget, multi-restart, a one-door lookahead), the hybrid two-direction build, hoarding stash items, buff always on the default hero. The skill parameter `s` in `[0, 1]` maps three ways: the move budget scales from Competent toward Strong; with probability `(1 − s) × e` a decision takes the second-best option (never an illegal one); noise is applied per decision class (arrangement, door, shelf) so "good at doors, bad at layout" can be modelled. The skill share σ of the 1-in-20 sketch is the measured slope of the outcome against `s` on paired seeds, not a free parameter; until it is anchored to human playtests (10 to 20 runs) results are reported as **bands, never as player win rates**.
7. **Competent: arrangement, doors, rewards.** *Arrangement* is a deterministic greedy local search: candidates are legal `(item, hero, cell, rotation)` tuples ordered by hero index, item ordinal, row, column, rotation, with ties to the lowest tuple; the score is a cheap proxy (expected damage over the first turns from `Forecast` plus link count from `Preview`), with the full `Forecast` only for the top `K` candidates; each step applies the best strictly improving single move (place, move, rotate, swap, remove-and-replace) and stops when none improves or the **move budget, counted in `Preview`/`Forecast` calls and never in time**, is spent; items are first assigned to heroes by marginal `Forecast` gain, then each hero is searched, in at most 2 passes. *Door:* the certain buff's fit to the commitment reading minus a risk term from the danger price, with the risk weight rising as build strength (the `Forecast` of the current layout against the door's danger) falls; the suggested hero and roster roles feed the fit. *Shelf:* take if the item's marginal `Forecast` gain after a trial placement is positive or it matches the committed direction and the tray has room, otherwise skip. *BuffClaim:* the hero with the largest `Forecast` gain, ties to the lowest index. *Start:* when no improving move remains or the budget is spent. Reward steps are run in System 5's order (Rule 9).
8. **Experiments, configs and A/B.** An experiment is `(seed list, policy id and version, config, catalog fingerprint)`. `RunConfig` is built from data: a base catalog snapshot exported from the authoring assets to a neutral file (JSON or TSV) by an Editor menu item with its hash stamped (the ScriptableObject loader is engine-bound and is not used by the console), plus a layered **patch** of `path = value` edits validated by the same catalog validation the game uses, hashed into the report. A patch must not change the RNG contract or the draw-count structure without bumping the version, because the restore invariants hard-code the draw counts. An A/B run changes one knob with the same master seed, the same index set and the same policy version; a sweep is one patch per grid point.
9. **Seeds.** `seed_i = Mix64(masterSeed, i)` with the splitmix64 finalizer (Formula 1), a harness-owned function that does not share System 1's generator, so a seed list is addressable ("master 7, runs 0 to 9999") and committed seed lists have ids and hashes. Never time-based. A **validation seed list** is kept separate from the lists used for tuning, to avoid overfitting. A pair of runs under two configs is keyed by the seed, not the run index. **A seed does not replay a run** (drops depend on the door and arrangement choices), so the replay artefact is the command log, and the report stores a command-log hash per run.
10. **Capture without retention.** The harness aggregates in streaming accumulators of fixed-size `long` counters and histograms, and discards the trace after each fight: it reads a `FightSummary` struct (room, outcome, reason, action count, per-hero damage and HP) and counters through a trace sink, and System 4's trace is released explicitly right after the callback (the trace lifetime and a `traceRecordCeiling` value are required from System 4; Open Questions). Per run: the outcome (Won, Lost with reason, Abandoned, Stopped, DriverStall), the room reached, a win/loss count per room, the door tier chosen per room, the buff-claim hero, offer take or skip, the committed direction and its strength. Per offer: the matching-card count (0 to 3) per room split by committed or uncommitted, with expected against observed per slot (Formula 7 of System 18). Pool coverage: per catalog item, offered and taken counts, and the distinct items offered per run. Per fight: actions used (histogram, sum, max), the HP margin on a victory, the defeat reason, and for each root action the pair `(depthMax, N)` bucketed with stated caps and an overflow bucket. Counters saturate and never throw; a saturation flags the report invalid. Full traces are kept only for sampled or flagged seeds (outliers, a `TechnicalStop`) and are reproducible from the seed list, the policy and the config.
11. **The run-defining predicate (user decision).** A run is **run-defining** iff the boss was defeated **and**, in the boss fight, a root action was classified **Detonation** by System 29's classifier (Payoff Presentation Rule 4) **and** it dealt at least `X` percent of the boss's maximum HP (`100 · D ≥ X · bossMaxHP`; `X` is **frozen at 50**, a user decision of 2026-11-14 from the concept re-review: it is not a tuning knob, because raising it is the same as lowering the boss's HP and would reach the target by relabelling; its registry safe range of 30 to 70 is used only to report how sensitive `P(run-defining)` is to it). The classifier is one pure function shared by the presentation and the harness (it lives in the engine-free core), so the player's bloom and the 1-in-20 measure the same thing, but the **run-defining threshold is separate from the classifier's**: System 29's thresholds are tuned first from the distributions of question 13 and then frozen as an input, and `P(run-defining)` may be tuned only through the drop cap, the lean, the key-item share, the pool, the doors, item effect magnitudes and boss HP, never by moving a classifier threshold or `X` (otherwise the target would be reached by relabelling, not by making the payoff harder to earn). This is the user's decision of 2026-11-14. The harness reports two separate metrics: the boss win rate and `P(run-defining)`; the 1-in-20 target (a goal of about 3 to 8 percent, to be tuned) applies to `P(run-defining)` of the `Competent` policy at its calibrated skill; calibration against human playtests is **[VS]**, so in the MVP `P(run-defining)` is reported as a band across `s` and is never compared with the goal as a PASS or FAIL; the report shows the curve of both against `s` (monotonic, with a top end well below 50 percent). Pillar 3's test, "nothing guaranteed, skill raises the odds", is a property of that curve.
12. **The catalogue of balance questions (MVP).** Each has a metric, the policies, a minimum N and a target (from the GDDs); the status is the MVP status: (1) the 1-in-20 `P(run-defining)`, N ≥ 4,000, ADVISORY (a tuning goal); (2) Purple price: the loss-rate gap between `IgnoreRoster` and `AnswerRoster` pairs of Competent, lower bound ≥ 10 points, N ≥ 1,000, ADVISORY (System 17 criterion 11); (3) buff worth keeping: boss win rate with the buff on against off, the margin rule of Formula 4 with `m = 2` points; deletion is recommended only on FAIL (upper bound below 2 points, reopening System 17 Rule 11) and INCONCLUSIVE means run more (about 8,000 to 10,000 per arm); ADVISORY; (4) tier dominance: the share of rooms where Competent picks one tier at most 70 percent, boss win rate by tier, and the three-channel ablation (buff off, item rows flattened), N ≥ 2,000, ADVISORY; (5) the lean: matching cards per offer committed against uncommitted (report only; the cap stays at or below `F = 2000`), ADVISORY; (6) pool coverage: the fraction of the roughly 16 droppable items a run sees (report only); (7) burst: the one-round hero-down rate by `(room, tier)`, with an extension for cursed heroes at the Vertical Slice (the structural bound of System 16 is also a BLOCKING structural test there, not here); (8) template answerability: win rate per `(template, room)` cell, N ≥ 200 per cell, ADVISORY; (9) boss above Purple, `T(P, 8) < T(boss)`: a static content check that belongs to the content validator (Systems 2 and 16), listed here as a cross-reference only and not a harness criterion; (10) the curse is a bet and (11) curse safety (System 19 criterion 25, BLOCKING) are **Vertical Slice**; (12) HP is not a resource: where pressure comes from, report only; plus (13) the distributions System 29 needs: `(depthMax, N)` per root action and actions per fight (for the ladder thresholds and the 90 s median target), report only; (14) the Unique Hook: at an **equal cell budget**, does the best split build beat the best one-hero build? `Competent` against `OneHeroStack`, both under `CellBudget(c)` with `c` the cell count of one hero's grid at that point (without the budget the split build wins on capacity alone, so a run without it is not this question), on the boss win rate and on `P(run-defining)`, with the margin rule of Formula 4 and `m = 3` points (provisional), N from Formula 3 for that margin (about 2,100 per arm, to be confirmed); ADVISORY in the MVP (reported, not gated) and a gate at the Vertical Slice (concept: Unique Hook and go/no-go); (15) the lean ceiling (Pillar 1): the same seeds and policy with `drop_bias_cap` at its value and at 0 (the off arm is a config patch, not the `IgnoreCommitment` policy); the ratio `P(run-defining, lean on) / P(run-defining, lean off)` has a ceiling that is **not yet set** (the earlier 1.5 was withdrawn by the concept's third-review decision D1, and System 18 computes the exact finite pool first; fourth-review note, 2026-11-14): until it is set the question reports the ratio and its upper 95 percent bound, INCONCLUSIVE when the off-arm interval includes 0 (run more), with N set from a power calculation for the ratio range of interest and not the default of 4,000 per arm, which cannot separate a ratio near 1.4 from 1.5 at a rate near 5 percent; the separate perceptibility floor is measured on matching cards per offer (question 5), not on this ratio; ADVISORY in the MVP and a gate at the Vertical Slice; the interval method for a ratio is added to Formula 4 before the gate, and until then both rates are reported with their Wilson intervals and the ratio of the point estimates; (16) build diversity: per 1,000 `Competent` runs, the number of distinct final-build fingerprints (the sorted set of item definitions) and the share of runs in the most common committed direction; report only (it measures the convergence risk in the concept's Design Risks).
13. **Degenerate strategies are probes, not goals.** Each tier-1 policy appears in the report as a win rate against Competent. The aim is that no degenerate policy beats Competent by more than a set margin and that `AlwaysPurple` and `AlwaysSafestDoor` both sit well below it; each knob is swept across at least two policies, because a single policy's skill confounds the knob.
14. **Statistics.** All in integers or fixed point, with `z` fixed at 1.96 as `196/100` (`z² = 3.8416`). Rates are scaled by 10⁹; every square root is an integer square root (floor) on scaled values with 128-bit intermediates, and interval ends round outward (the lower end down, the upper end up) so an interval is never narrower than the exact one, which keeps the bytes identical across runtimes; `n = 0` is `NOT ASSESSED` with the interval printed `[0, 1]`. A single rate uses the **Wilson interval** (Formula 2); the difference of two independent rates uses the normal interval of Formula 4 (Newcombe's hybrid-score interval is **[VS]**); a paired comparison on the same seeds (**[VS]**) uses **McNemar-style counts** `b` (wins only in A) and `c` (wins only in B) (Formula 5) and the discordant counts are always reported, because the seed does not make two configs' runs identical once the choices diverge, so the pairing's correlation is measured and never assumed. The default experiment size is **10,000 runs** per cell and the minimum is **1,100** (Formula 3). A claim "A beats B by at least `m` points" is the one-sided rule of Formula 4: **PASS** iff the lower 95 percent bound of the difference is at least `m`; **FAIL** iff the upper bound is below `m`; otherwise **INCONCLUSIVE**, reporting the extra runs needed. With about 10 looks in one sweep the primary metrics are named in the config before the run and a Bonferroni level (`z ≈ 2.576` one-sided at 0.5 percent) is used for the others. A rate is never printed without its `n`.
15. **The report (canonical text).** A per-run TSV (seed, outcome, room reached, defeat cause, key metrics, command-log hash) sorted by seed, and a summary of aggregates, in UTF-8 with LF line endings, invariant culture, integers only (ratios as numerator and denominator), a fixed key order, no wall-clock time, machine name or path inside the hashed part, a header that stamps the rules and content versions, the catalog fingerprint, the RNG contract version, the policy id and version, the config and patch hashes, the seed-list id and hash, N per cell, the harness version, the git SHA and the decision rules used, and a last line `CHECKSUM fnv1a64 <16 hex>` (the same function as System 5's snapshot and System 7's tables). The compact page for a sweep holds: the pass/fail table for questions 1 to 16 (estimate, 95 percent interval, target, ADVISORY or BLOCKING flag, status), win rate by room and tier, the skill curve, door-tier choice share by room, the degenerate-strategy bars, matching cards per offer, pool coverage, and the defeat hazard per room. A metric with no implemented policy or too few runs prints `NOT ASSESSED` with the reason (for example `N = 312 < required 1,100`), never `0` or `pass`; a run cut off by a timeout is flagged `INCOMPLETE`.
16. **The command line.** Verbs: `run` (one scenario), `sweep` (a grid of patches), `compare` (two reports on a metric with a tolerance), `report` (re-render a stored result), `verify-golden`, and `bench` (runs per second, allocations, and time per command). In the MVP only `run`, `compare`, `report` and `verify-golden` ship; `sweep` and `bench` are **[VS]**. Arguments: `--catalog`, `--seeds`, `--policy`, `--config`, `--threads`, `--timeout-s`, `--out`. Exit codes: 0 ok; 1 usage; 2 invalid config or catalog; 3 a rejected command or rule fault in a run; 4 timeout (a partial `INCOMPLETE` report); 5 determinism or golden mismatch; 6 a regression found by `compare`. Progress goes to standard error, never into the report. A per-run step cap (counted in commands) keeps determinism; a global wall limit only produces `INCOMPLETE`.
17. **Parallelism and determinism ([VS]; the MVP console is single-threaded).** Seeds are sharded by run index into contiguous blocks; each worker has its own session and accumulator and no shared mutable state (the catalog is immutable and shared); the merge is a fixed reduction by shard index. The report hash for 1 thread and for 8 threads is identical. Draw counts are audited on every completed run (`doors == 43`, `drops ≤ 48`, `intents` by System 5 Formula 1); a mismatch is a harness defect.
18. **Parity with Unity (user decision).** Fixture layers: (a) RNG vectors (seed, stream, request sequence, expected words, final state); (b) bounded and weighted draws; (c) canonical snapshot bytes with their checksum; (d) scripted runs (seed plus command script producing the canonical System 4 trace, stored whole so a diff reports the first mismatch). Their expected values come from an **independent oracle**, such as the generator's published reference code or a script under `tools/`, never from either C# runtime. Both runtimes read the same LF files (the test code does the I/O; the core does none); a `.gitattributes` file is a prerequisite because `core.autocrlf` is on. The parity fixtures live in `Assets/Tests/EditMode/Harness/` and run in Unity and in the console. Everything here is blocked on System 1's PRNG ADR. Because the divergence risk is in sorting, comparers, culture and `Dictionary` order and not in integer arithmetic, the core uses ordinal comparers, sorts only on a unique key, `InvariantCulture`, `\n` and never `Environment.NewLine`, bans `string.GetHashCode`, and enforces this with analyzers in both builds. Every report prints the RNG and rules versions; if Unity parity is not being enforced by CI, the report says so.
19. **CI and cost.** On every push: a `dotnet` job (build, analyzers, the harness's own tests, and a smoke experiment of 50 to 200 runs on a toy config compared with the committed golden report, about 60 s). Scheduled (nightly or weekly, off the pull-request path): the full sweeps of 1,000 or more runs per policy on the real data, a few tens of minutes with parallelism and a hard timeout that yields `NOT ASSESSED`. A `game-ci/unity-test-runner` EditMode job (**[VS]**; until then parity is run by hand through the Test Runner window before each milestone) runs the parity fixtures (it needs the Unity licence secrets; a 6000.6.3f1 image and personal-licence activation are unverified). Performance target to validate: at least about 2,000 full runs per second per core, so 100,000 runs in under a minute on 8 threads (a planning figure, not a measurement). Reports are artifacts with retention, so a gate decision can cite a retained file.
20. **Scope tiers and order of work.** The MVP is built in two stages (user decision). **Stage A, right after the combat core spike:** a fight-only driver over fixed, fixture-supplied arrangements that reports question 13, the `(depthMax, N)` distribution per root action and the actions per fight (it needs Systems 12 and 36 only, not System 5's `RunView`); it feeds the freezing of System 29's thresholds. **Stage B:** a single-threaded console with `RandomLegal`, `Competent` and three degenerate policies (plus the `IgnoreRoster` and `AnswerRoster` pair), Wilson and the margin rule, the accumulators, the canonical checksummed report, the determinism, golden-report, statistics and stream-audit tests, the parity fixtures run by hand, and the smoke job. **[VS]:** threads, the paired and Newcombe statistics, `sweep`, `bench`, the Unity parity CI job, the assembly-reference scan, the `Strong` policy and the remaining degenerate set, multiplicity control beyond the named primaries, the curse questions (10 and 11), the cursed-hero burst extension, session reuse, the human calibration of σ, and the full report page graphics. **The harness cannot be built before** an engine-free command-driven core exists (today the code is MonoBehaviour-based: `RunManager`, `CombatManager`): Systems 5, 12 and 36 must be implemented first, so the GDD fixes the contracts now and the implementation follows the combat core spike.

### States and Transitions

| Subject | State | Trigger | Result |
|---|---|---|---|
| Experiment | Planned | A config names a seed list, a policy and a patch | Versions and hashes are stamped before any run. |
| Experiment | Running | `run` or `sweep` | Shards play runs; accumulators fill; progress goes to standard error. |
| Experiment | Complete | Every shard finished | Fixed-order merge; the report is written with its checksum. |
| Experiment | Incomplete | The wall limit is hit | A partial report flagged `INCOMPLETE`; exit code 4. |
| Run | Playing | `Play(seed, policy, config)` | Commands are sent until Ended, Stopped, Abandoned or `DriverStall`. |
| Run | Counted | The run ends | The result is folded into the accumulators; the trace is released. |
| Metric | Assessed, PASS, FAIL or INCONCLUSIVE | The interval is computed | Reported with `n` and the interval. |
| Metric | NOT ASSESSED | No policy, or `N` below the required size | Reported with the reason, never as 0 or pass. |

## Formulas

All harness arithmetic is on integers or fixed point; no `float` in anything that is hashed. Statistics use `z = 1.96`, `z² = 3.8416`.

**Formula 1: seed derivation.** The splitmix64 finalizer applied to `masterSeed + (i + 1) × 0x9E3779B97F4A7C15` (mod 2⁶⁴): `z ← (z XOR (z ≫ 30)) × 0xBF58476D1CE4E5B9`; `z ← (z XOR (z ≫ 27)) × 0x94D049BB133111EB`; `seed_i = z XOR (z ≫ 31)`. *Examples:* `master = 0`: `seed_0 = e220a8397b1dcdaf`, `seed_1 = 6e789e6aa1b965f4`, `seed_2 = 06c45d188009454f`; `master = 7`: `seed_0 = 63cbe1e459320dd7`, `seed_1 = 044c3cd7f43c661c`. (The first value for master 0 is the well-known first output of splitmix64 for seed 0; the fixtures take their expected values from an independent oracle.)

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `masterSeed` | ulong | any, 0 valid | seed-list id | The list's master seed. |
| `i` | ulong | `0..N−1` | run index | Run index. |

**Formula 2: Wilson interval for `x` of `n`.** With `p = x / n`: `centre = (p + z²/2n) / (1 + z²/n)`, `half = z · √(p(1−p)/n + z²/4n²) / (1 + z²/n)`, interval `[centre − half, centre + half]` clamped to `[0, 1]`. *Examples:* `n = 0`: NOT ASSESSED, interval printed `[0, 1]`; `x = 0, n = 20`: `[0, 0.1611]`; `x = 10, n = 20`: `[0.2993, 0.7007]`; `x = 1000, n = 1000`: `[0.9962, 1]`; `x = 50, n = 1000`: `[0.0381, 0.0653]`.

**Formula 3: minimum sizes.** For a single rate at worst case `p = 0.5`, a half-width `h` needs `n ≥ (z / 2h)²`: `h = 0.03` gives `n ≥ 1,068` (the default minimum is 1,100); for the difference of two independent rates with equal arms the worst case is `n ≥ (1.386 / h)²`, `h = 0.03` gives 2,135 per arm. For a rare target (`p ≈ 0.05`) a relative precision of about ±20 percent needs about 1,800 runs. The default experiment is 10,000 runs, whose worst-case half-width is about 1 point. Question 1 uses `n ≥ 4,000`: at `p = 0.05` the half-width is `1.96 × √(0.05 × 0.95 / 4000) ≈ 0.0068`, about ±13.5 percent of the target.

**Formula 4: the margin rule.** For a difference `d = pA − pB` with interval `[lo, hi]` and a margin `m`: PASS iff `lo ≥ m`; FAIL iff `hi < m`; else INCONCLUSIVE with the extra size `n′ = ⌈z² (pA qA + pB qB) / (d − m)²⌉` per arm (`q = 1 − p`). *Example:* `pA = 0.54`, `pB = 0.40`, `m = 0.10`: `n′ = ⌈3.8416 × (0.2484 + 0.24) / 0.0016⌉ = 1,173` per arm.

**Formula 5: paired difference.** With `n` paired seeds, `b` wins only in A and `c` wins only in B: `d = (b − c) / n`, `var ≈ (b + c) / n² − (b − c)² / n³`, interval `d ± z √var`. *Example:* `b = 60, c = 30, n = 1000`: `d = 0.03`, `var = 8.91 × 10⁻⁵`, half-width `0.0185`.

**Formula 6: draw-count audit (inherited).** From System 5 Formula 1: a full run makes `1 + 7 × 6 = 43` calls on `doors` (1 at the run start, then 3 tier draws and 3 variant draws for each of 7 rows), at most `6 × 8 = 48` on `drops` (6 per victory over 8 rooms), and `Σ` over the 9 bindings of `2 × 12 × E` on `intents`; the harness asserts these for every completed run.

**Formula 7: the 1-in-20 measure.** `P_rd = k_rd / n` with `k_rd` the runs that defeated the boss and contained, in the boss fight, a root action classified Detonation (System 29 Formula 1) with `100 · D ≥ X · bossMaxHP` (`X` default 50); the boss win rate is `k_win / n`; both use Formula 2 for their intervals and are reported at `s = 0, 0.25, 0.5, 0.75, 1` on paired seeds. *Example:* `k_rd = 410, n = 10,000`: `P_rd = 0.041`, Wilson `[0.0373, 0.0451]`, inside the 3 to 8 percent goal.

## Edge Cases

Format: *condition: outcome.*

**Runs and policies**
- *A policy returns an illegal command:* the facade returns `Rejected`; it is counted; at most 3 retries, then `DriverStall`.
- *A stale serial from a policy bug:* the harness wraps the serial; a stale reject is a harness defect and counted.
- *A TechnicalStop during a run:* counted, the first diagnostic kept, the run is in the denominator; the report lists the count and the seeds.
- *A Draw or the 200-action cap:* a loss, per System 12.
- *An auto-skipped reward step (nothing grantable, an empty offer):* needs no policy input; the driver advances.
- *A policy needing randomness (the random baseline):* uses only its own labelled stream; the gameplay streams are never touched.
- *The seed is zero:* valid (System 5 Rule 13).
- *A `Mix64` collision in a seed list:* checked for distinctness when the list is created.
- *Abandoned runs:* a bot never abandons, but if one occurs it counts in the denominator, as System 5 Rule 12 requires.
- *A catalog patch that changes the draw-count structure:* rejected by the validator unless the version is bumped.

**Statistics and reports**
- *`n = 0`:* `NOT ASSESSED` with the interval printed `[0, 1]`. *`x = 0`, `x = n`:* intervals are computed and clamped to `[0, 1]`; `n` is printed.
- *`N` below the required size:* `NOT ASSESSED` with the reason; never a pass.
- *Many metrics in one sweep:* only the named primaries use the plain level; the rest use the Bonferroni level.
- *The paired design is weak (the streams diverge after the first changed decision):* the discordant counts are printed and the pairing's value is reported, not assumed.
- *A counter saturates:* the report is flagged invalid.
- *The wall limit is reached:* a partial report flagged `INCOMPLETE`, exit code 4.
- *Floating-point or culture creeping into a hashed field:* forbidden; the canonical writer rejects it and the analyzers ban the APIs.
- *A report regenerated from the same inputs:* byte-identical, including at 1 and 8 threads.

**Hosting and parity**
- *Unity and the console disagree on a fixture:* Unity is authoritative; the harness run is invalid until the divergence is fixed (exit code 5).
- *The Unity CI job is unavailable:* the dotnet job still runs, the report states that Unity parity was not enforced.
- *The Editor is open on the project:* the console runs unaffected; batchmode is never used on the open project.
- *A `.cs` file leaks an engine reference into the core:* the engine-free assembly fails to compile; the linked build fails with it.
- *The RNG algorithm is still undecided:* the parity fixtures and golden reports are blocked; the report prints the RNG contract version as `UNPINNED`.

> *Edge cases drawn from the specialists' failure lists (systems-designer, qa-lead, gameplay-programmer, technical-director).*
